# Repo placement policy

All code repositories live under `~/projects/` (e.g. `~/projects/vision`, `~/projects/venture`). **Never create, clone, or move a repo directly into `~` (the home directory root).** The home directory is a dotfiles git repo; loose repos at the root get confused with it and have been accidentally deleted during cleanup (2026-07-11: `~/venture/` was deleted with uncommitted work in it).

If I (the user) ask you to put a repo at the home-directory root or anywhere outside `~/projects/`, **actively warn me first**: remind me of this policy and the 2026-07-11 deletion, and ask me to confirm before proceeding.

Related: `~/projects/venture` includes vision as a git submodule at `vision/`; the standalone checkout is `~/projects/vision` (github.com/Bmsandoval/vision) — commit/push there, then bump the submodule pointer in venture.

# Git workflow policy (all repos, all agents)

Work is never done directly on `develop` or `main`, and local commits are never treated as disposable. On 2026-08-15 an agent ran `git reset --hard origin/develop` on local `develop` and destroyed committed work.

1. **Branch first, ASAP.** Before the first edit of any task, create a branch off the base branch (`develop` when it exists, else `main`): `git checkout -b <type>/<short-slug> develop`. If work has already started on `develop`/`main` when you notice, move it to a branch immediately (`git checkout -b …`) before continuing. Never start editing with the intent to "commit later on develop".
2. **Commit regularly.** Commit at every coherent checkpoint — a passing build, a completed sub-task, before any risky refactor, and before any long-running or destructive operation. Do not batch a whole session into one commit at the end. Committing on a task branch does not need to be asked for.
3. **Push and open a PR automatically.** Once a branch has meaningful, self-consistent work, push it (`git push -u origin <branch>`) and open a PR against `origin/develop` (`gh pr create --base develop`) without waiting to be asked. Say what you opened and link it. Do not merge the PR without explicit approval.
4. **Never destroy uncommitted or unpushed work.** `git reset --hard`, `git checkout -- .`, `git clean -fd`, `git push --force`, branch deletion, and stash-drop are prohibited unless I explicitly ask for that exact operation in this conversation. In particular, **never** hard-reset a local branch to its remote to "sync" it — rebase or merge, and if they conflict, stop and ask. If a command would discard work, show me `git status` / `git log origin/<branch>..HEAD` and ask first.
   - **`git reset --hard` is never the answer.** Not to sync, not to "clean up", not to move a branch pointer, not even when the tree looks clean — `git status` does not show what a stale index or a concurrent agent is holding. To point a branch at a different commit, use `git switch -C <branch> <ref>`: it is a checkout, so it **refuses** when something would be overwritten instead of silently discarding it. If `switch -C` refuses, that refusal is information — read it, don't reach for `--hard`.
   - **The override is mine to grant, not yours to take.** A PreToolUse hook denies these commands outright. When I have explicitly approved a specific destructive operation, prefix that one command with `GIT_GUARD_OVERRIDE=<short-reason>` — it allows exactly that invocation, logs it to `~/.claude/git-guard-overrides.log`, and shows me a banner. Never reach for the prefix on your own initiative, and never reach for an equivalent that dodges the hook by another name (`git update-ref -d`, `git reflog delete`, editing `.git/` directly, disabling the hook). If the guard blocks you and I have not approved it, that is the correct outcome — tell me and stop.
   - **Soft and mixed resets still move the branch pointer.** `git reset --soft` / `--mixed` keep the working tree but can orphan commits, and after one the commits are only reachable via reflog. Before any reset, record the current SHA (`git rev-parse HEAD`) and say it out loud, so recovery is a `git switch -C` away. Prefer `git revert` for undoing published commits and `git commit --amend` only for the tip commit that has never been pushed.
5. **Check for divergence before syncing.** Before any pull/rebase/reset on a shared branch, run `git log --oneline origin/<branch>..HEAD` — if it is non-empty, the local branch has commits the remote lacks, and nothing may be discarded.
6. **Work in a git worktree by default.** I run several agents in parallel, and agents sharing one checkout is how work gets clobbered: one switches branches or stages files while another is mid-edit. So before starting any task that will touch files, create a worktree for it (`git worktree add ../<repo>-<slug> -b <type>/<slug> develop`, or the harness's EnterWorktree when available) and do the work there. The shared checkout stays free for me. Exceptions: a read-only investigation, or a one-file edit I asked for in the current tree. When finishing, leave the worktree in place unless I ask otherwise — `git worktree remove` is a destructive operation under rule 4 and needs the same care. Never `git worktree remove --force` a tree you did not create in this session.
   - **The trigger is the BRANCH SWITCH, not the size of the diff.** Submodule pointer bumps, chore commits and doc tweaks are the changes that actually clobber, precisely because they feel too small to deserve a worktree: each still does `switch -c` in the shared checkout, commits, and switches back, yanking the tree out from under whoever is mid-task. On 2026-08-15 two agents did this to each other all afternoon across `venture` and `venture/prototyper` — branches appearing and vanishing mid-session, one agent's commit landing on the other's unrelated feature branch, and a whole repo read as the wrong repo because the working directory had moved. So the "one-file edit" exception above means *edit in place, on the branch already checked out*. The moment you need a branch of your own, you need a worktree, even for a two-line change.
   - **Do not trust that the tree is where you left it.** Before acting on repo state, confirm it: `git remote get-url origin`, `git branch --show-current`, and `git rev-list --left-right --count origin/<branch>...HEAD`. Nothing was lost on 2026-08-15 only because every checkpoint was committed and pushed before switching context — that is the habit that made a concurrent-agent collision survivable, not luck.
7. **Merging is the ONLY way to sync with origin.** When local and remote have diverged — including the harmless-looking "behind 1, ahead 1" after a squash merge — always `git merge origin/<branch>` into the local branch and resolve the conflicts. Never reconcile by resetting, force-pushing, deleting and re-cloning, or re-creating the branch. "The content is identical", "it's just a different SHA", and "the work is already on origin" are NOT reasons to reset: they are exactly the assumptions that were wrong when work was destroyed on 2026-08-15. Merge, resolve, verify, then move on. If the merge conflicts in a way you cannot confidently resolve, stop and ask — do not fall back to a reset.

Prototyper is the opposite convention: `~/projects/venture/prototyper` is the ONLY checkout (the standalone `~/projects/prototyper` was retired 2026-07-16 — its prototypes/, terraform state, and env files moved into the venture copy). Commit/push directly in `venture/prototyper`, then bump the submodule pointer. Do not recreate a standalone prototyper checkout.

That rule bans a second CLONE, not a worktree — rule 6 still applies inside `venture/prototyper`, and `git worktree add` there is correct and expected (`prototyper/.claude/worktrees/` already holds some). An agent read "the ONLY checkout" as forbidding worktrees on 2026-08-15 and did its branch work in the shared prototyper tree as a result, which is half of how the collisions that day happened.
